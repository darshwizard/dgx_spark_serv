Important Flash Next startup finding
Two starts crossed our memory guards during post-load weight repacking. The
previous model was unloaded first; the second start began with ~118.7 GiB
available and reached ~1.7 GiB before cancellation completed. This was a RAM
allocation spike, not a thermal stop or a cgroup-limit OOM.

The community documents a temporary repacking dip and a 2 GiB hard / 6 GiB for
30 seconds soft floor:
https://github.com/devopsfortunato/Qwen3.8-Flash-Next-FP4-Local-DGX-Spark#what-startsh-and-scriptspreparesh-do
We adopted those floors, retaining immediate thermal and missing-sensor stops.
Our machine still crossed 2 GiB on the next attempt.

A second community report identifies retained CUDA load-time allocations and
uses this allocator mitigation:
https://huggingface.co/diffbot/Qwen3.8-Flash-Next-FP4-Local-DGX-Spark#how-it-fits-in-one-spark
  PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True
Adding ONLY that variable to our previous serving configuration passed repacking
and completed all benchmarks. No new weights, precision changes, vision removal,
MTP changes, kernel patches or lower safety floors were needed. About 29 GiB
remained as planning began; the full successful run's minimum was 17.49 GiB.
This validates the mitigation on this image/driver/checkpoint pairing; other
pairings need measurement. Save startup logs even when the eventual boot works.

Build benchmark layers without changing serving dependencies
The two Dockerfiles under experiments/large-models-20261102/build/ install only
the benchmark wheels with pip --no-deps. Build those wheels outside the minimal
image so Git-based version detection works:

  git clone https://github.com/SeraphimSerapis/tool-eval-bench.git
  git -C tool-eval-bench checkout 2ad584631702f042295862a363396ccbc6ac0fe9
  git clone https://github.com/eugr/llama-benchy.git
  git -C llama-benchy checkout e9be344578cec17745066b220798b80a0d2686d3
  python3 -m pip wheel --no-deps --wheel-dir wheels ./tool-eval-bench ./llama-benchy

Place wheels/ beside the Dockerfiles, build the forum base first for Super,
then build the corresponding benchmark image. Both benchmark CLI help commands
must work. Retain the resulting immutable image ID in the job specification.
This adds harnesses; it does not upgrade Torch, vLLM or CUDA.

Staging and running on this queue host
Use an enrolled account and SSH/SFTP, following the live /agents guide. Stage
weights under workspace/models/<checkpoint basename>, scripts under workspace/
code, and persistent caches under workspace/cache. Inside the job these are
/workspace/models, /workspace/code and /workspace/cache. For example:

  hf download nvidia/Qwen3.8-Flash-Next-FP4-Local \
    --revision b9ce18a6887e18c089fdea8509a33e63429a3300 \
    --local-dir workspace/models/Qwen3.8-Flash-Next-FP4-Local

Stage scripts/model_campaign_job.py and scripts/paired_model_bench.py. Actual
spec.json files are preserved under each model's artifacts. Submit GPU work
only through compute-job. Do not launch another GPU server beside the queue.
The owner-run example controller and runtime-switch helper are in the artifact
directory; their ROOT/REPO/SSH settings and backup paths are specific to this
host and must be adapted for another installation. They switch runtimes only
with an idle queue, launch host telemetry and an external watchdog, acknowledge
clock-profile phases, download results, and restore the original runtime.

To serve on a different installation, use its local compute policy and map
the /workspace paths accordingly. launch.json contains the server-only command
and its required environment, so the serving setup can be reproduced separately
from our queue controller and benchmark handshakes.

Controls
Temporary job limits: 20 CPU quota, 118 GiB charged memory, 16 GiB shared memory,
no anonymous job swap. CUDA allocations are not fully charged to this cgroup:
actual host-available memory is the primary pressure signal. The root watchdog
samples at ~100 ms; stop at <2 GiB available or hottest ACPI >=90 C. For the final
Flash run, also stop after 30 continuous seconds below 6 GiB. Job admission for
benchmark phases needs >=3 GiB. Fail closed on controller or sensor loss.
No host swappiness, firmware, EC, or fan-curve changes. Host swap stays enabled.
Original queue limits/runtime/reference files and clock ceilings were restored.

Benchmark controls and analysis
See LARGE-MODEL-PROTOCOL-20261102.txt. Cache resets require
VLLM_SERVER_DEV_MODE=1 on these isolated loopback servers and success=true in the
API response. No model reload between the four normal/capped/capped/normal
phases. CPU-only orchestration regression:
  python3 tests/smoke_paired_client.py
Energy/host-activity regeneration after extracting raw-run.tar.gz:
  python3 scripts/workload_energy.py --events RUN/result/bench/events.jsonl \
    --sensors RUN/telemetry/sensors.jsonl --out workload-summary.json
Power readings are integrated only over workload event boundaries. This is
GPU-reported energy, not whole-machine energy; it does not fully account for
CPU, NVMe, fan and power-supply costs. A wall meter is needed for that comparison.
